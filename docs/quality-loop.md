# Human-workbench quality loop

Use this loop after a meaningful batch and before delivery. Inspect the affected user journey; a closed issue, a source review or a successful build alone does not prove it works.

## Close the finding across entry points

Record the user's starting point, intended result, observed failure and the owning object. Trace equivalent actions through project/global views and ordinary/advanced controls. A request shortcut fixed in one composer must not leave the saved-workflow composer inconsistent. Check the existing capability before inventing another configuration or workflow.

Keep a short issue checklist linking each residual finding to its implementation and verification. A new observation joins that checklist; it does not erase earlier steering or resume unrelated parked work.

## Maintain shared interaction contracts

- **Reading:** one primary surface for a result. Headings identify work; activity records changes; detailed history retains original evidence. Use the same safe Markdown behavior, including reader-scoped heading and footnote links. Do not load remote media or execute supplied HTML.
- **Attention:** activity opens at the latest meaningful update. A user reading history keeps their position, including during late backfill or group merges. Category counts exclude unrelated and technical records.
- **Execution:** show the actual executor, operation and age of the latest observation. Animation requires an authoritative running state; waiting and silence are not fabricated progress. Unattended retries have shared finite bounds, termination checks and an actionable exit.
- **Input:** request composers share composition-safe Enter submission and Shift+Enter editing. Apply this to equivalent request fields, not every textarea. Preserve drafts, disabled states and idempotency.
- **Receipts:** preserve an acknowledged write before refreshing observations. Failed or stale reads must not turn a successful start/save into another submission. Reconcile receipts monotonically; later Stop and terminal state may supersede them.
- **Configuration:** preserve inherited versus explicit empty selections. Show effective values before editing them; an unavailable observation is not an empty configuration. Copying a role must not discard its capabilities. Ordinary work must not require changing permanent permissions or estimating an unfamiliar quota.
- **Knowledge:** retain source and verification evidence. Allow an owner to withdraw obsolete lessons reversibly; do not silently rewrite frozen work or treat every generated sentence as reusable knowledge.

## Verify and publish a bounded change

1. Update the owning PRD before substantive behavior. Update UED when the interaction changes. Keep the operating/API guidance consistent with actual defaults, including legacy behavior.
2. Add meaningful regression coverage for the failure and important state boundaries. Run appropriate focused checks, then the required suite once; repeat only for new changes or unresolved failures.
3. Operate the affected path with ordinary controls in English and Simplified Chinese. Include long content, desktop/narrow layouts, keyboard/focus, asynchronous updates and failure recovery. Check wrapping, contrast, balanced actions, duplicate content and context retention.
4. Distinguish synthetic/model-free checks, live provider execution, publication and deployed verification. Record test-only intervention and unpassed checks privately. Do not consume model turns during unchanged waits.
5. Have a different reviewer inspect the actual candidate and resolve findings. Publish exact reviewed files and hashes; exclude local configuration, private knowledge, transcripts and captures.
6. Refresh affected delivery artifacts. Verify the deployed website and current app where they changed, then update the issue with the PR and evidence. Preserve paused exercises and independent benchmark gaps explicitly.

After the walk-through, remove accumulated copy, duplicated explanations and obsolete controls before adding more UI. Capture a new reusable rule only when the observed failure adds something to this contract.
