# Attachments in goal inputs

Status: implemented candidate; independent review, browser acceptance, real provider reading and publication remain separate pending stages. Read with the [interaction contract](goal-attachments-ued.md), [human workbench](human-workbench-prd.md) and [quality loop](quality-loop.md). Requirements are not completion evidence.

## Bounded implementation contract

Use owner-authenticated raw-byte uploads, with a stable upload request ID, a draft scope and an encoded display name. Keep the ordinary two-MiB JSON limit. Store immutable originals and generated PNG thumbnails under the private application data directory. Detect content independently of the browser MIME hint; decode only signature-matched PNG/JPEG/GIF/WebP with a maintained decoder and its 20-million-pixel guard. Decode failure retains a usable original and a file card.

Submission fields carry ordered attachment IDs; the server resolves and verifies the immutable manifest, including aggregate byte limits, before accepting work. Initial goal/run manifests remain frozen. Continuations record supplements with their receipt and affected stage/recovery history. Include inherited same-project files in follow-up context without changing the original request. Existing records with no attachments retain their behavior.

Before native or Multica dispatch, verify the digest and materialize generated file identities in GWI-controlled private application state, outside the worker's actual writable roots, including separate independent-verification copies. Derive those roots on the server from the effective executor and frozen role, not merely from the project workspace argument. Native Intake coordination is read-only: ordinary project-local `.local/state` remains usable there. Connected workers use their isolated execution workspace; independent verification uses its actual writable copy. Native workspace-write fallback cannot safely stage inside that same project: require an independent private `GWI_DATA_DIR` or isolated executor and report that boundary before dispatch. Never write through worker-controlled workspace directories: checking a pathname before writing cannot prevent a concurrent parent-directory replacement. Preserve the existing sandbox and artifact-preview exclusion. A readable private copy and a provider reading it are separate evidence.

This revision repairs three implementation findings without replacing prior product/design or QA history. Register an entire selected batch synchronously before preparation/upload begins, so every outstanding item blocks submission. Removal and exact-version clearing invalidate its pending preparation, receipt lookup and upload results; no later batch item or reselection may repopulate that draft. Bind agent `run.start` calls to the server's actual parent run and calling stage, ignoring caller-supplied ancestry. Child runs inherit that stage's effective frozen inputs, including its continuation supplements, without changing accepted siblings or earlier attempts.

## User result

A person can give a project screenshots, documents or other local files with a concrete request, using a file button, file paste or file drop. They can recognize each added file through a simple preview, remove a mistaken selection, recover an interrupted draft and submit once. The recorded goal and each authorized execution retain the exact submitted material. A filename in the interface without readable execution input does not satisfy this result.

Adding or previewing a file is local preparation and starts no model work. Keep the existing project, pipeline, team, scheduler, source/account admission and native permission decisions. No attachment setup page, new execution mode or permission form is required.

## File support and simple previews

Accept individual browser-provided files, including multiple selections. Each file may contain up to 10 MiB (10 × 1024 × 1024 bytes); the selected files for one submission may total up to 32 MiB. These are upload/storage resource boundaries, not model execution quotas. Enforce actual byte lengths on the server, including across separate uploads. Keep ordinary JSON request limits intact; file transport needs its own bounded validation. Directories, directory traversal, remote URL fetching and arbitrary server-path imports are excluded.

| Input content | Required simple preview after upload | Interpretation boundary |
| --- | --- | --- |
| Verified PNG, JPEG, GIF or WebP raster image | A bounded thumbnail with filename and size. A static frame is sufficient for GIF. | Decode only supported raster content. Images exceeding a 20-million-pixel preview boundary use a file card; the original remains usable. |
| Valid UTF-8 text, including code, Markdown, JSON, CSV and logs | A literal escaped excerpt of at most 4,000 characters, with a truncation indicator when needed. | Do not render supplied HTML, SVG, Markdown media or scripts. Empty text shows an explicit empty-file state. |
| PDF, office documents, archives, other binary or unrecognized content | A file card with filename, detected type when known, size and ready state. | The card is the simple preview. No embedded document viewer, archive extraction, OCR, conversion or promise that every execution model can interpret the format. |

All regular files within the byte boundaries can be retained as opaque input; the preview table is not a file-extension allowlist. Browser MIME types and extensions are hints, never authority to render active content. Inspect content before choosing a preview; a malformed image or incompatible encoding falls back to a file card with an explanation. A preview failure does not discard an otherwise durably uploaded original. A failed or incomplete upload is a separate, blocking condition.

File paste means file/image items actually exposed by the browser clipboard event. Ordinary text paste still edits the request. Mixed clipboard content adds the file items once and preserves available plain text at the caret. HTML-only clipboard content grants no remote-image download permission. If the browser exposes no file, explain the limitation and retain the file-button alternative. Do not request blanket clipboard access. File drops are limited to the visible input area; text/link drops keep native text behavior without fetching their destinations.

## Draft, submission and history

- Persist original bytes and any preview files in ignored local private application data. The tab-local draft stores scoped attachment references and state, not file bytes or public URLs. Preserve filenames, order and ready uploads through navigation, locale change, modal dismissal and reload while that tab session remains available. G1/G2 deliberately share the existing project outcome draft; follow-ups, questions, pipelines and attempts retain their distinct contexts.
- Upload completion means the server durably acknowledged bytes, project ownership, attachment identity and content digest. Restored pending uploads without durable completion become interrupted items requiring retry/reselection or removal. Browser storage or local-storage failure must be visible; keep the current draft usable and do not promise reload recovery when it cannot be established.
- Give each upload a stable request identity within its project/draft. If its response is lost, reconcile or retry that same upload identity and bytes to recover the receipt, rather than creating duplicate stored items. Reusing an upload identity with different bytes or metadata is a conflict. Interrupted transfers still need explicit retry/reselection; no automatic model work or pipeline replay is involved.
- Removing a file changes only the unsent draft. It must not delete an original file on the user's device or a frozen reference used by submitted work. A late upload response cannot reinsert a removed item, enter a different project or clear a newer draft. Repeated selection of the same bytes with the same displayed filename keeps one draft item; equal names with different digests remain distinguishable. Use stable order for the submitted manifest.
- All shortcuts to the same consuming action use its selected text/files and upload/submission guard. A goal-header recovery shortcut cannot dispatch without the material prepared in the visible recovery composer. Ordinary and advanced continuation of the same confirmed target/basis retain one instruction draft; advanced model/configuration choices remain separate. If the target/basis changes, retain the previous draft in its original scope and require deliberate review before reuse.
- Disable work submission while any selected item is uploading, interrupted, failed, missing or beyond the aggregate byte boundary. Explain the affected file and offer retry/reselect or remove. Preserve ready siblings and text after a partial batch failure. The user can deliberately remove the failing item and submit the remaining material. Never silently start a text-only request after a file failed.
- Snapshot text and the complete selected attachment manifest for one submission. Bind its existing target identity, ordered attachment IDs, names, sizes and server-computed digests to the idempotent request. An unchanged retry after a lost response returns its recorded result; the same key with changed content is a conflict. Editing text or attachments creates a different submission identity. Extend continuation receipt handling where it currently has only recovery-generation guards; do not assume those guards already provide attachment-aware idempotency.
- Clear only the exact acknowledged draft version, after recording its receipt and before observing refreshed work. Failed/stale observations cannot remove that receipt, re-upload accepted bytes or invite another dispatch. A late receipt preserves a newer draft and cannot navigate away from a newer selection. An uncertain write stays recoverable with its original identity.
- Attachments are immutable input, pinned with goal/run configuration and continuation-attempt history. A retry retains prior material and adds only deliberately submitted supplements to the affected attempt. Accepted independent work stays intact. Removing a later draft or refreshing configuration never replaces old bytes or digests. Missing/corrupt frozen bytes require attention before an affected dispatch; never substitute a same-named local file or replay the whole pipeline.
- A follow-up retains the parent relationship and frozen earlier attachment references as historical context. Historical attachment presence grants no new authority; include only material reachable through that same project's authorized frozen context, with omissions visible. Do not copy private files into general knowledge, templates or public results automatically.
- Keep uploaded-but-unsent originals for the recoverable draft session. After the tab session ends they may remain orphaned in private state; this increment adds no scheduled expiry or global cleanup UI. Referenced goal/run/attempt material remains retained with that history. Any later cleanup must prove there are no draft, pending-receipt or historical references before deleting bytes; a local storage failure never permits silent eviction of referenced material.

## Project security and execution handoff

Uploads, attachment metadata, preview/content reads and reference validation require the existing owner session or an explicitly authorized project-scoped actor. Resolve the owning project from stored identity; a supplied project ID, opaque attachment ID or digest alone grants no access. Reject cross-project reference injection at every start, continuation and read boundary. Do not add a new agent upload/control grant implicitly. Keep loopback binding, same-origin mutation checks, private caching rules and sandbox/approval decisions.

Use generated storage identities rather than filenames as paths. Validate metadata lengths, actual bytes, aggregate bytes, regular-file status, realpath containment and symlink boundaries. Execution handoffs live under private application state in `attachment-inputs/<project>/<workspace-digest>/<run>/<attempt>/`; their parent directories must remain outside worker write scope. Application state within a read-only project workspace is allowed; application state within an actual worker write root blocks handoff and requires an independent private state location. A caller cannot supply or weaken this execution scope. No handoff write or repair may follow a worker-controlled `.local` symlink, even if its target appears safe when inspected. Escape displayed names and snippets. Never use supplied names/content as shell commands, URLs or execution instructions. Serve only verified raster previews inline through authenticated project access; other bytes remain literal text or an explicit download. No application static route or unauthenticated shared URL may expose private input.

Execution copies and generated previews remain ignored private material. Exclude them from prepared-source patches, public fixtures, commits and publication candidates; attaching a file grants no permission to publish it. Keep original project files untouched.

Freeze a manifest containing at least attachment ID, project, display name, byte length, detected media type and SHA-256. Authorized native/Multica coordinators and the affected delegated stages must receive a readable reference to the exact bytes, plus their untrusted-input status. Use maintained runtime interfaces and controlled private application-state copies readable under existing runtime permissions. Keep staging outside all worker write roots, including Multica's system temporary roots. An execution checkout alone does not include uploaded local state. `src/workspaces.ts` intentionally denies `.local` through artifact preview; do not weaken that output boundary for uploads. Verification copies also exclude private runtime paths, so their attachment handoff must be explicit.

Check digest and readable handoff before affected work is dispatched. If a configured runtime cannot access the material within its existing scope, show the actual blocker and next owner action; do not broaden its sandbox, read credentials, start blind model work or claim success from a prompt listing filenames. A real provider-backed read must be recorded separately from model-free storage/handoff checks. Attachment content remains task data and cannot authorize tools, publication or cross-project actions by itself.

## Integration and role handoff

Accepted continuation files and instructions remain bound to the exact goal control revision, router, run, stage and failed attempt while account approval is pending. Approval pins that recovery identity across asynchronous account checks; a superseding instruction makes the older approval fail. Only matching, unexecuted account-admission holds may follow the original failed attempt without consuming its pending instructions. Ordinary approval applies an unconsumed supplement exactly once and verifies the original bytes before replacement work; an admission hold does not discard it. Stop, a changed target or a superseding recovery cannot supply an earlier pending supplement.

Retained browser continuation uses the same unsent text and attachment selection as its ordinary recovery entry. Browser choice remains explicit, pinned to the exact attempt and current browser revision; attachment IDs join that same durable submission identity. Closing the dialog or a failed authorization retains the draft. A returned-finding action consumes only its stated review note and retained verifier evidence: it stays unavailable while this continuation draft has unsent files, with an explanation, rather than silently omitting those files.


The candidate carries attachment references through Intake create, follow-up, retry/resume, direct Run create and stage resolve/continue paths used by G1–G8, including frozen execution context and durable receipts. Records without attachments preserve their contracts. See [the implemented transport](API.md#private-goal-attachments), `src/attachment-types.ts` and the independently authored synthetic cases in `test/attachments.test.ts`, `test/attachment-http.test.ts`, `test/attachment-drafts.test.ts` and `test/platform.test.ts`. A completed subordinate handoff cannot consume supplements by silently reusing its accepted child: the API returns an explicit handoff blocker and directs the owner to the affected subordinate work.

The design owner applies the shared UED to every inventory row. The implementation owner supplies source/API checks and a reviewable candidate; an independent QA owner reviews that candidate and operates the acceptance cases below. Operations updates API, usage and delivery guidance to actual behavior. GWI assigns concrete owners/reviewers in their stages. Publication is a separate reviewed step with exact paths, privacy/dependency checks and any created PR linked to the task. This product stage neither publishes nor establishes later acceptance.

## Scope decisions and exit

“All goal inputs” includes executable recovery instructions G6–G8. It does not convert project/role/pipeline configuration, knowledge editors, stop reasons, review findings, manual-result forms or in-flight steering into upload surfaces. Those inputs have different contracts; extending them needs a separate request. A binary file card fulfills simple preview; a full PDF/office viewer, OCR, remote import, directory upload and automatic archive processing are excluded. Attachment-only initial goals and replacement/removal of historical input are excluded.

The runtime transport and permitted file interpretation still depend on actual configured capabilities. Implementation must prove a usable handoff or report that boundary; this specification supplies no runtime permission. A request to add excluded behavior or an unavailable authorized handoff is consequential scope evidence for GWI/owner resolution, rather than a reason to silently broaden the feature.

This stage exits with input coverage, supported behavior, exclusions and acceptance examples specified. Later implementation, independent acceptance, real runtime access and publication retain separate status. Repair only the responsible boundary when a later check fails; retain accepted work and stop on an unchanged blocker or a genuine owner decision.
